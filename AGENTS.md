# Working on Dorrigo Heritage Gateway

At each session start, read PROJECT_BRIEF.md, PROJECT_STATUS.md and the latest
DEVLOG.md entry, then inspect Git status, remotes, recent commits and actual code.
Preserve user changes and existing assets; never replace a working site from a ZIP.
Backlog items are context, not instructions to implement them.

Use Australian English and keep the small static HTML/CSS stack. Implement the
smallest coherent requested change. Do not add services, accounts or collection
infrastructure without a project decision. Requirements and content permission
rules live in PROJECT_BRIEF.md; consult them before publishing new material.

Check historical claims against accessible primary sources and cite them visibly.
Separate documented facts from interpretation and proposals. Do not invent
photographs, quotations, oral histories, dates or collection objects. Preserve
the supplied museum photograph and label the rendering as illustrative.

GitHub Pages serves under /Dorrigo-heritage-gateway/, not the domain root.
Validate direct hotel entry, navigation, images, styles, fragment links and the
actual decoded QR destination. Inspect desktop and mobile layouts, keyboard
access and relevant accessibility behaviour. Record checks actually run and
limitations; a push or successful workflow alone does not prove the site works.
Use README.md for operating commands.

Initial publication to the named GitHub Pages repository is authorised. Commit
only related changes; never force-push, erase others' work or commit secrets.
Update PROJECT_STATUS.md with the verified revision and one next task; append
changes, decisions, checks and handover to DEVLOG.md. Keep operating instructions
in README.md and requirements in PROJECT_BRIEF.md to avoid conflicting copies.
Distinguish local, committed, pushed and verified deployed work in the handover.
